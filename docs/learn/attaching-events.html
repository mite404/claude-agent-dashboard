Attaching Events to Tasks

The job: make GET /tasks return each task with a list of the tools it ran. Simple goal. Ten separate concepts hiding inside it.

The spine

SQLite and Drizzle are honest: they report the widest possible type (string, | null). Your React components want the narrowest ('pre' | 'post', never null). Every concept below is the same question wearing a different hat: where do you put the narrowing?

And what "narrowing" actually means

Reducing how many values are possible. That count has a name — cardinality — and every concept below is a move down this ladder: 

string                    → ∞ possible values
string | null             → ∞ + 1  (the mapper's job: get rid of the +1)
TaskStatus                → 8       ($type<>() on the column)
'pre' | 'post'            → 2       (as, or a type guard)

Framing borrowed from Lauren Tan, “Type Narrowing in TypeScript”.

Concept 01

The list isn't stored anywhere

The hook_events table has no column that holds a list. There is no "array" type. Each row is one event, carrying a task_id that says which task it belongs to.

Task abc "has" two events because two rows point at it. The list only exists once JavaScript builds one.

          Concept 02
          
Two queries, not fifty-one

          

            The obvious way is a loop: for each task, ask the database for its events. Fifty tasks
            means fifty-one round trips (one for the tasks, fifty for the events). This is the
            classic
            N+1 query. inArray asks once for all of them.
          

          
const ids = tasks.map((task) => task.id);        // → ['abc','def','ghi']
.where(inArray(hookEventsTable.taskId, ids))     // SQL: WHERE task_id IN ('abc','def','ghi')

          

            What comes back is a jumbled pile — everybody's events mixed together. Sorting the pile
            into per-task buckets is a Map, done in JavaScript. Two trips instead of
            fifty-one.

            The guard you must not forget
            

              WHERE task_id IN () with nothing inside is invalid SQL.
              Bail out early when there are no tasks.
            

          

          

        


        
        

          Concept 03
          
Missing and empty are two different things

          
completedAt?: string          // the key might not be there at all
completedAt: string | null   // the key is there, holding nothing

          

            Databases only produce the second kind. TypeScript's ? only accepts the
            first. So completedAt: row.completedAt fails even though both "mean"
            missing. ?? undefined bridges it.
          


          

            
Two shapes, four assignments — which compile?

            

              
              
            

            

          


          

            Grammar, not value
            

              ? is grammar for describing a type. It cannot appear when you
              are building an actual object. { completedAt?: value } is not a
              thing.
            

          

          
So which do you write when the target prop is optional?

          

            
Two forms · toggle the tsconfig flag

            

              
              
            

            

          

          

            On the wire they are identical — JSON.stringify drops
            undefined values, so both send {"id":"1"}. They differ only in
            memory: form A leaves 'completedAt' in obj true, form B leaves it false.
            Nothing in this codebase branches on that, and everything crosses a JSON boundary before
            it reaches React. Take A.
          

          

            Two things to avoid
            

              In form B, test for presence (!== null), never
              truthiness — row.completedAt ? … silently drops an empty string. And
              never declare completedAt?: string | null: that is three states,
              and every consumer has to handle all three. One flavour of nothing per field.

          Concept 05
          
$inferSelect — the shape the table hands back

          

            This comes from Drizzle. Not SQL, not TypeScript. You wrote the table once. While you
            did, TypeScript worked out what a row would look like if you selected from it. Drizzle
            parks that answer on the table under $inferSelect, so you never write the
            shape twice.
          

          
const toHookEvent = (row: typeof hookEventsTable.$inferSelect): HookEvent => ({ ... });
//                       └── "whatever shape a SELECT on hook_events gives back"

          

            typeof is required because hookEventsTable is a
            value, and you are asking about its type.
          


          

            
Rename the column in schema.ts — see who notices

            

              toolName: text() →

            The payoff: rename a column and the derived line errors immediately,
            pointing at the exact spot. A hand-written copy just quietly goes wrong.
          

          
So why infer at all — why not declare the row type upfront?

          

            Because the schema is the declaration. Writing
            type TaskRow = {…} alongside it creates a
            second, independent declaration of the same fact, and TypeScript has no
            way to check one against the other. They are not wrong relative to each other; they are
            two separate opinions that happen to agree today. That is the cost — not typing effort,
            the absence of a check.
          

          

            

              What a hand-written copy would have to get right · tasksTable, 20 columns

            src/types/task.ts declares Task, HookEvent and
            TaskStatus by hand. That is not inconsistency, it is the rule:
            declare the contract, infer the consequence.

              Inference is only trustworthy when the thing you infer from is authoritative.
              The arrow must point from truth toward consequence, never the reverse — which is why
              Task is hand-written and the row type is not.
            

          


          

        


        
        

          Concept 06
          
as — telling the compiler to trust you

          

            SQLite stores text. It has no idea the phase column only ever holds
            'pre' or 'post'. So Drizzle honestly reports
            string, which is wider than HookEvent allows.
          

          
phase: (row.phase ?? 'pre') as HookEvent['phase'],

          

            HookEvent['phase'] is a lookup — the same square-bracket
            syntax you use on objects, but pointed at a type, so it returns
            'pre' | 'post'. Using the lookup instead of typing the union out means this
            line updates itself if the union changes.
          


          

            
Put a value in the database column and run the mapper

            

              
              
              
              
            

            

          


          

            

              as runs no code. It checks nothing, converts nothing,
              and disappears at compile time. That is the trade — which is exactly why it belongs in
              one small converter and nowhere else.
            

          

          

        


        
        

          Concept 06b
          
The option as never mentions

          

            Concept 06 called as "the trade" — you get the narrow type, you give up the
            check. But there is a third option that is not a trade at all: a
            type guard. It is the same if statement you were going to
            write anyway, with a return type that lets TypeScript read it.
          

          
const isTaskStatus = (v: unknown): v is TaskStatus =>
  (VALID_STATUSES as readonly unknown[]).includes(v);
//                     └── "if this returns true, v is a TaskStatus" — and TS believes it


          
This repo has a comment doing a type's job

          

            
src/server.ts · line 70 and line 77

            

              
              
              
            

            

          


          
Assertion functions — the same idea, but it throws

          

            A cousin from TypeScript 3.7. Where a guard returns true/false
            for you to branch on, an assertion function narrows everything after the call
            and throws if the claim is false:
          

          
function assertTaskStatus(v: unknown): asserts v is TaskStatus {
  if (!isTaskStatus(v)) throw new Error(`not a status: ${v}`);
}

assertTaskStatus(status);
// every line below this one now sees status as TaskStatus

          

            Use a guard when a bad value is expected and you want to respond (a
            400). Use an assertion when a bad value means
            something upstream is broken and you want a loud crash with a useful
            message.
          


          

            Also worth stealing: satisfies
            

              VALID_STATUSES is currently a hand-written second copy of
              TaskStatus — Concept 05's sticky-note problem, living in the server. Add
              as const satisfies readonly TaskStatus[] and the two get cross-checked. A
              planted typo produced:
              TS2820: Type '"runnning"' is not assignable to type 'TaskStatus'. Did you mean
                '"running"'?
            

          


          

            

              as is telling the compiler trust me. A type guard is
              showing your work. Same runtime cost, and the banana from Concept 06
              gets caught instead of waved through.
            

          

        


        
        

          Concept 07
          
$type<>() — relabeling a column without touching the database

          

            SQLite knows four storage types: TEXT, INTEGER,
            REAL, BLOB. A status column is just text. But that column only
            ever holds eight specific words, because VALID_STATUSES in
            src/server.ts rejects everything else at the door.
          


          

            
Toggle the label — watch runtime stay identical

            

              
              
            

            

          


          
It is a cousin of as, filed in a better place:

          

            

              
              as
              $type<>()
            

            

              Where
              at one use site
              at the column definition
            

            

              Reach
              that one expression
              every query, everywhere
            

            

              Written
              once per use
              once, ever
            

          

          

            The claim "status is one of eight words" is true about the column, not about
            one particular read of it. So the column definition is the honest home for it.
          


          
Not just for unions

          
metadata: text({ mode: 'json' }).$type<Record<string, unknown>>(),

          

            mode: 'json' does the real work — stringify on write, parse on read.
            $type only labels what comes back, so you stop narrowing
            unknown at every read site. You usually want both.
          


          
The catch: the narrowing has to be true

          

            

              progressPercentage: integer().$type<0|25|50|75|100>()
            

            

              
              
            

            

          

          

            The other failure mode
            

              Concept 07's trap is narrowing that is not true. There is a second one:
              narrowing that is true but not worth it. As Lauren Tan puts it, "it can be easy to get
              carried away with making your types extremely precise." A type nobody can satisfy is a
              type everyone routes around with as.
            

            

              "When we restrict what we can do, it's easier to understand what we can do."
              — Runar Bjarnason
            

          


          

        


        
        

          Concept 08
          
A spread throws away what a guard proved


          

            
Step through the handler

            

              
              
              
            

            

            

          


          

            The guard narrowed body.sessionId. The spread copies body's
            general shape (Record<string, unknown>), not the specific
            fact you just proved. The knowledge is lost.
          

          

            

              The fix is to restate the key, not to cast it. Naming the property
              again re-reads the narrowed value. as string also silences the error, but
              it asserts something you had already proven — and the linter correctly flags
              it as pointless.
            

          

          

        


        
        

          Concept 09
          
Cast last, not first

          

            The linter warned that a null-guard was dead code. Both lines look the same. They are
            not.
          


          

            

              Pick an ordering — trace what TypeScript believes at each step
            

            

              
              
            

            

          


          

            

              The cast made a true statement look false. Handle reality first,
              while TypeScript still knows what reality is. Then narrow.

Every row leaves through a mapper

          

            src/server.ts now has a matched pair at the top:
            toHookEvent and toTask. Storage leaves things nullable; the
            frontend's types do not. These two functions are the entire border crossing.

          🎬 Blooper 33
          
The schema that typed itself into a corner

          

            Two lines in src/db/schema.ts quietly switched off type checking for the
            entire API:
          

          
parentSessionId: text().references(() => sessionsTable.id),  // sessions → sessions
parentId: text().references(() => tasksTable.id),            // tasks → tasks


          

            
Ask TypeScript to resolve tasksTable

            

              
              
              no annotation
            

            

          


          

            any spreads downhill. Every query built on that table became
            any, every result became any, and error messages in
            src/server.ts turned into nonsense that moved around whenever anything
            changed.
          

          
parentId: text().references((): AnySQLiteColumn => tasksTable.id),
//                          └── "returns a column, take my word for it"

          

            Self-referencing foreign keys are not a mistake — they are how you store a
            tree in a flat table. tasks.parentId is the subtask
            nesting the tree view depends on. The data genuinely refers to itself, so the type
            genuinely refers to itself, and inference has nowhere to start. The annotation supplies
            the base case a recursive definition needs. Nothing changes at runtime.
          

          

            Why it went unnoticed for months
            

              tsconfig.app.json excludes src/server.ts and
              src/db. bun run build has never type-checked the API.
              Files outside the build's reach rot silently.

              building an object. And as string lies: the value really can be

              twenty times. (A CHECK constraint would be real enforcement — but it's a migration,

              Narrowing attaches to the reference body.sessionId, not to
              body. Restate the key —
              { ...body, sessionId: body.sessionId } — which re-reads the narrowed
              value. Don't reach for as string: you already proved it.
